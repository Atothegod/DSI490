ภาพรวม
เอกสารนี้ล็อกข้อกำหนดการออกแบบ Agent 1 (Unified Flood Intake & Support) ที่ทีมตกลงร่วมกัน ใช้เป็นภาคผนวกของ Project Handoff เดิม และเป็นฐานสำหรับเขียน schemas.py, DSPy Signatures และ Backend Rules

หลักการ: Agent 1 รวบรวมข้อเท็จจริงและจัดการ Memory จัดลำดับเบื้องต้นรายเคสด้วยกฎและจัดกลุ่มตามพื้นที่ (ข้อ 7) ไม่วางแผนช่วยเหลือ และไม่อ้างว่าส่งความช่วยเหลือแล้ว

1.1 Hybrid Handoff
เหตุทั่วไป: เก็บข้อมูลขั้นต่ำ ให้ผู้ใช้ยืนยัน แล้วจึงส่ง
เหตุเร่งด่วน: เมื่อมี urgent_flags ส่งทันทีแม้ข้อมูลไม่ครบ แล้วถามต่อภายหลัง
หลังส่ง: ส่ง incident_updated ด้วย Incident ID เดิมเมื่อข้อมูลสำคัญเปลี่ยน (ดูข้อ 2.5)
ข้อมูลไม่ครบแล้วหยุดคุย: เก็บเป็น Draft ใน PostgreSQL
1.2 urgent_flags
บันทึกข้อเท็จจริงที่ผู้ใช้บอกตรง ๆ ไม่ใช่การตีความความรุนแรง ค่าเริ่มต้น: people_trapped, injury_reported, help_requested ตรวจจับด้วย keyword และ Gemini แบบ OR พร้อมเก็บแหล่งที่มาของแต่ละ flag (ข้อ 6.3) flag หมายถึงพบสัญญาณที่ต้องดำเนินการต่อทันที flag สั่งส่งทันทีแยกจาก priority รายเคส (ข้อ 7.1) ส่วนการวิเคราะห์ระดับพื้นที่เป็นหน้าที่ของ Agent 2
1.3 การไหลของข้อมูล + Technical ACK
ประชาชน → Agent 1 → Agent 2 → เจ้าหน้าที่ v1.2: Agent 2 หรือเจ้าหน้าที่ส่งสถานะดำเนินงานกลับมาได้ แยกจากสถานะการส่ง (ข้อ 7.4) และยังไม่ทำ LINE Push ใน MVP
ACK หมายถึง Agent 2 รับและบันทึกรายงานสำเร็จ ไม่ใช่มีคนอ่านหรือส่งคนไปแล้ว
ทุกการส่งมี event_id ไม่ซ้ำ เพื่อให้ Agent 2 ตัดรายการซ้ำได้
บันทึกลง DB ก่อนส่งเสมอ ถ้าไม่ได้ ACK ให้ retry และเก็บสถานะใน outbox (ตาราง escalation_events)

2.6 Personal Data Policy v1.0
LINE User ID ใช้ภายใน Agent 1 เท่านั้น Agent 2 ได้ reporter_ref แบบสุ่ม รหัสภายในสร้างจาก LINE User ID ด้วย HMAC-SHA256 และ secret key ฝั่ง server ซึ่งยังถือเป็นข้อมูลที่เชื่อมโยงถึงบุคคลได้
ชื่อและเบอร์ไม่บังคับ รายงานส่งได้แม้ไม่มี
เสนอให้ทิ้งเบอร์ครั้งเดียวเมื่อขอความช่วยเหลือหรือมี urgent_flags แจ้งวัตถุประสงค์ด้วย template และบันทึก consent_at, purpose ถ้าปฏิเสธหรือข้ามไม่ถามซ้ำ เบอร์ที่ผู้ใช้พิมพ์มาเองไม่ถือเป็นความยินยอม (ข้อ 6.13)
Agent 2 เห็นแค่ contact_available และ contact_ref การเปิดดูเบอร์จริงต้องผ่าน endpoint ที่ตรวจสิทธิ์และมี audit log
ปิดบังเบอร์โทรที่ทางเข้าก่อนบันทึกข้อความและก่อนส่ง Gemini ทุกส่วน (ข้อ 6.2)
พิกัดส่งให้ Agent 2 ได้เมื่อ (v1.2): ผู้ใช้ได้รับคำอธิบายและเลือกให้แนบตำแหน่งกับรายงานนั้น (LocationShareConsent, ข้อ 6.10) ใช้ได้ทุกประเภทเคส หรือ needs มี rescue / evacuation ตามนโยบายเดิม (รอทบทวนกับผู้รู้ด้าน PDPA ข้อ 8.1) การมี urgent flag อย่างเดียวไม่ให้สิทธิ์ส่งพิกัด และข้อความแจ้งอย่างเดียวไม่ทำให้ความยินยอมสมบูรณ์ตามกฎหมาย ต้องสอดคล้องกับนโยบายที่ทีมรับรอง กรณีอื่นส่งระดับตำบล/หมู่บ้าน
คำขอลบข้อมูลยกเลิก consent ทันที และระงับการแนบพิกัดทุกเงื่อนไขระหว่างรอลบ
ไม่อนุญาตส่งต่อ ≠ ขอลบข้อมูล: เก็บเป็นคนละสถานะ ไม่อนุญาตส่งต่อ = ไม่แนบข้อมูลนั้นกับรายงาน ส่วนขอลบ = ลบตามข้อ 3.5 และส่ง data_deletion_requested
ข้อความแจ้งครั้งแรก: แสดงท้ายคำตอบแรกครั้งเดียว ไม่ขวางเหตุด่วน (ข้อ 6.13)
ข้อมูลเดโมใช้ข้อมูลสมมติหรือไม่ระบุตัวบุคคล
3. Memory Management
Incident State เป็นแหล่งความจริงเดียวของข้อมูลเหตุการณ์ ส่วน Summary ใช้รักษาความต่อเนื่องของบทสนทนาเท่านั้น
3.1 Incident Lifecycle
สถานะมี 4 ค่า: draft, submitted, closed, abandoned การแก้ไขหลังส่งเป็น event incident_updated ไม่ใช่สถานะใหม่

incident lifecycle · 4 สถานะ
event ที่เกิดระหว่างอยู่ในสถานะ submitted ไม่เปลี่ยนสถานะ และ closed ไม่ย้อนกลับเป็น submitted
close_reason
ความหมาย
user_resolved
ผู้ใช้ยืนยันว่าสถานการณ์คลี่คลาย

ไม่มีการอัปเดตครบ 14 วัน ไม่ได้แปลว่าปลอดภัย

ผู้ใช้แจ้งว่าแจ้งผิดหรือเป็นเรื่องซ้ำ
out_of_service_area
draft ที่พบว่าอยู่นอกจังหวัดและไม่มี urgent flag (ข้อ 6.5)

ทุกการปิดเหตุที่เคยส่งแล้วส่ง Close Event พร้อม close_reason ให้ Agent 2
ปิดจาก draft ได้เฉพาะ out_of_service_area และไม่ส่ง event เพราะ Agent 2 ไม่เคยรู้จักเหตุนั้น (ภาพด้านบนยังไม่แสดงเส้นทางนี้)
เหตุที่ส่งแล้วแต่พบภายหลังว่าอยู่นอกจังหวัด ไม่ปิดเอง ให้ส่ง incident_updated ที่เปลี่ยน service_scope แล้วให้ Agent 2 ตัดสิน
Draft ที่ไม่เคลื่อนไหว 7 วันเปลี่ยนเป็น abandoned
"ความเคลื่อนไหว" นับจากข้อความที่ให้ข้อมูลเกี่ยวกับ incident นั้นเท่านั้น รวมถึงการยืนยันค่าเดิม (confirmation)
Incident ที่ปิดแล้วไม่ reopen ถ้าเป็นเหตุเดิมกลับมา ให้สร้างใหม่พร้อม related_incident_id และนำตำแหน่งเดิมให้ผู้ใช้ยืนยัน
Draft ที่มี urgent_flags ไม่มีทางเป็น abandoned เพราะถูกส่งทันที
3.2 Incident Matching
แต่ละ conversation มี active_incident_id
ผูกอัตโนมัติ: มี incident เปิดอยู่เรื่องเดียว และข้อความไม่กล่าวถึงตำแหน่งใหม่
ถามยืนยัน: กล่าวถึงตำแหน่งอื่น มีหลาย incident เปิดอยู่ หรือ LLM ไม่มั่นใจ

เร่งด่วนและไม่ชัดว่าเหตุไหน: สร้าง Provisional Incident ส่งทันที แล้วค่อยถามเชื่อมโยง

6.9 ลำดับการถามและการหยุดถาม
เหตุทั่วไป: จุดเกิดเหตุ (location_area + พิกัดเป็นทางเลือก) → situation → needs → affected_people + vulnerable_people → water_level

ข้าม field ที่ known, unknown, declined หรือ unanswered
water_level, contact, พิกัด และจุดสังเกต ถามครั้งเดียว field บังคับถามได้สูงสุด 2 ครั้ง ส่วนจำนวนคนถาม 2 ครั้งเฉพาะเคสที่ต้องการความช่วยเหลือหรือมี urgent flag เหตุทั่วไปถามครั้งเดียว (v1.2) เก็บ ask_count และ last_asked_at
ถามครบแล้วไม่ได้คำตอบ ตั้งเป็น unanswered ไม่ใช่ unknown

ขอยืนยันรายงานแล้วจบรอบการถาม กลับมาถามเมื่อผู้ใช้แก้ไขหรือมีข้อมูลใหม่

6.10 พิกัดและการอนุญาตส่งต่อ
v1.2: ขอจุดเกิดเหตุทุกเคสที่แจ้งเหตุ GPS เป็นทางเลือก พิมพ์ที่อยู่หรือจุดสังเกตแทนหรือข้ามได้ ไม่ถามเมื่อถามความรู้อย่างเดียว ยังไม่ทราบให้บันทึกว่ารอข้อมูลตำแหน่ง ไม่เดา และไม่ขวางการส่งเคสด่วน
ข้อความขอ (template): "จุดเกิดเหตุอยู่ที่ไหนคะ? แชร์ตำแหน่ง หรือพิมพ์หมู่บ้าน ตำบล และจุดสังเกตได้ค่ะ หากแจ้งแทนผู้อื่น กรุณาระบุตำแหน่งของจุดเกิดเหตุ ตำแหน่งจะใช้ระบุจุดเกิดเหตุและแนบรายงานให้ผู้ดูแลรายงานเพื่อประสานความช่วยเหลือ หากไม่สะดวก สามารถข้ามได้ค่ะ" พร้อมปุ่ม [แชร์ตำแหน่ง] [ข้าม] คำแนะนำเรื่องเลื่อนหมุดใส่หลังตรวจหน้าจอ LINE ที่ใช้จริง
ไม่แสดงชื่อภายในอย่าง "Agent 2" ให้ประชาชนเห็น
คำขอที่ยังรอคำตอบเก็บเป็น LocationShareRequest ส่วน LocationShareConsent สร้างเมื่อผู้ใช้แชร์ตอบคำขอนั้นแล้วเท่านั้น บันทึกวัตถุประสงค์ รุ่นข้อความแจ้ง และ message ID ของคำขอกับคำตอบ คำขอเปิดรอ 24 ชั่วโมง
แยก 3 การกระทำให้ชัด: ขอให้แชร์ตำแหน่ง / อนุญาตส่งต่อ / ขอลบ ใช้ปุ่มและสถานะคนละชุด
พิกัดที่ส่งมาก่อนเห็นข้อความแจ้ง หรือไม่ชัดว่าตอบคำขอใด ต้องถามขออนุญาตก่อน (template location_consent_confirm)
ไม่อนุญาตส่งต่อ → ไม่แนบพิกัดกับรายงาน แล้วถามจุดสังเกตหรือพื้นที่กว้างขึ้นแทน เป็นคนละสถานะกับการขอลบ
แชร์ตำแหน่งมาอย่างเดียวโดยยังไม่มีเหตุ → ไม่สร้างเคสทันที ถามก่อนว่าต้องการแจ้งอะไร
GPS → ตำบล: ตำบลที่ใกล้ที่สุดเป็นเพียงตัวเลือกเสนอ แล้วถามยืนยัน ห้ามบันทึกเป็นตำบลที่ยืนยันแล้วอัตโนมัติ ยังไม่ยืนยัน = เก็บพิกัดพร้อมสถานะ "รอยืนยันตำบล"
ไม่เก็บที่อยู่ (address) ที่ LINE ส่งมากับตำแหน่ง เก็บเฉพาะพิกัด
consent ไม่เปลี่ยน needs เป็น rescue และไม่หมายถึงมีเจ้าหน้าที่รับงาน
คำขอลบข้อมูลยกเลิก consent ทันที และระงับการแนบพิกัดผ่านเงื่อนไข needs ด้วย ระหว่างรอลบ
เก็บพิกัด 30 วันหลังปิดเหตุ แล้วลดเหลือระดับตำบล (ข้อ 3.5) รวมสำเนาในประวัติ field, event และ outbox ไม่ใช่เฉพาะช่องข้อมูลหลัก

6.12 การยืนยันรายงาน (v1.2)
คำยืนยันผูกกับสรุปฉบับล่าสุดที่ส่งถึงผู้ใช้สำเร็จแล้วเท่านั้น เหตุด่วนไม่ต้องยืนยัน
รับ confirm_report เฉพาะเมื่อมีคำขอยืนยันที่ส่งสำเร็จและยังรอคำตอบ Gemini ตีความ "แค่อยากแจ้งไว้ก่อน" เป็น confirm_report ผิดในการทดสอบจริง จึงต้องมีกฎนี้
ข้อมูลเปลี่ยนหลังแสดงสรุป → ต้องแสดงสรุปใหม่และยืนยันใหม่ แม้พิมพ์ "ยืนยัน" มาในข้อความเดียวกัน
คำขอยืนยันหมดอายุใน 24 ชั่วโมง แล้วแสดงสรุปล่าสุดอีกครั้ง (ตัวเลขนี้เป็นนโยบายระบบ ไม่ใช่ข้อกำหนดกฎหมาย)
ผู้ใช้ถามความรู้แทรก → ตอบคำถาม แล้วยังรอคำยืนยันสรุปเดิม ตอบเรื่องอื่น → แสดงสรุปเดิมอีกครั้ง
พบ urgent flag → ส่งทันที ยกเลิกคำขอยืนยันที่ค้าง และไม่แสดง "ขอยืนยันรายงาน" อีก
ข้อความเหตุด่วนให้สั้น: สายด่วน + สถานะการส่งต่อที่เกิดขึ้นจริง + คำถามที่จำเป็น 1 ข้อ ไม่ใส่คำรับทราบ
6.13 ข้อความแจ้งครั้งแรก เบอร์โทร และการกรองก่อนส่ง Gemini (v1.2)
แยก 3 เรื่องออกจากกัน: ยืนยันรายงาน อนุญาตใช้ข้อมูล และส่งต่อเหตุเร่งด่วน การยืนยันรายงานไม่ได้แปลว่ายินยอมส่งเบอร์หรือพิกัด
ข้อความแจ้งครั้งแรก (privacy_notice_v1, รอทีมตรวจถ้อยคำ)
ระบบจะใช้ข้อมูลที่คุณแจ้งเพื่อจัดทำรายงานและส่งต่อให้ผู้ดูแลรายงานเพื่อประสานความช่วยเหลือค่ะ
ไม่ใช้คำว่า "เท่านั้น" เพราะข้อความถูกเก็บเป็นความจำและส่งประมวลผลที่ Gemini ด้วย ใช้ "ผู้ดูแลรายงาน" แทน "หน่วยงาน" จนกว่าจะมีหน่วยงานจริง
แสดงท้ายคำตอบแรกครั้งเดียว ไม่มีปุ่ม ไม่ต้องกดยอมรับ และไม่ขวางเหตุด่วน บันทึกรุ่นที่ผู้ใช้เห็น เปลี่ยนข้อความแล้วแสดงใหม่ 1 ครั้ง
ก่อนทดลองกับผู้ใช้จริงต้องมีข้อความฉบับเต็ม (ระยะเวลาเก็บ ผู้รับผิดชอบ สิทธิขอลบ) ดูข้อ 8.1
เบอร์โทรที่พิมพ์มาเอง
ไม่ตั้งเป็นความยินยอมอัตโนมัติ เก็บเป็นสถานะรอยืนยัน ไม่แนบรายงาน ไม่ส่ง Gemini และไม่ส่งต่อ
ถามด้วยปุ่ม [ให้ติดต่อกลับได้] [ไม่ต้องการ] พร้อมแจ้งวัตถุประสงค์และผู้รับข้อมูล ไม่ต้องการ → ลบทันที
ระยะเวลาพักเบอร์เมื่อผู้ใช้ไม่ตอบยังไม่ตกลง (เสนอ 24 ชั่วโมง) ต้องมีฐานและนโยบายรองรับ ดูข้อ 8.1
เบอร์ถูกปิดบังตั้งแต่ทางเข้า (ข้อ 6.2) ข้อความ ประวัติแชต และ log จึงไม่มีเบอร์ เหลือเฉพาะระเบียนที่รอยืนยันที่ต้องลบ และ log ต้องไม่เก็บข้อความดิบของผู้ใช้
การกรองก่อนส่ง Gemini: เบอร์โทร (ทำแล้ว) เลขบัตรประชาชน 13 หลัก และบ้านเลขที่ด้วย regex ชื่อคนภาษาไทยกรองได้ไม่ครบ เป็นข้อจำกัดที่ยอมรับ

ต้องตรวจสอบ
ข้อมูลไม่พอประเมิน หรือมีเพียง help_requested ("ช่วยด้วย") — ยังส่งทันทีตาม urgent flag

คำนวณด้วยโค้ดล้วน ไม่ให้ Gemini ตัดสิน เก็บเหตุผลเป็นรายการ เช่น ["people_trapped", "vulnerable:bedridden"] และเวลาประเมิน
ข้อมูลไม่พอ ≠ priority ต่ำ ใช้สถานะ "ต้องตรวจสอบ" พร้อมเหตุผล และไม่ขวางการส่งต่อเร่งด่วน
ระดับน้ำจากผู้แจ้งใช้เป็นตัวเพิ่มระดับได้ ห้ามใช้ลดระดับ เกณฑ์ตัวเลข (เช่น ซม.) รอทีมกำหนด
ประเมินใหม่เมื่อข้อมูลเปลี่ยน เก็บประวัติระดับเดิม เหตุผล และเวลา ไม่ลดระดับเอง ยกเว้นผู้ใช้แก้ว่าแจ้งผิด
Agent 2 หรือเจ้าหน้าที่ปรับได้ บันทึกผู้ปรับ เหตุผล และเวลา และ Agent 1 ไม่เขียนทับค่าที่ปรับแล้วโดยอัตโนมัติ
urgent flag ยังเป็นตัวสั่งส่งทันทีแยกจาก priority และไม่แสดงระดับให้ประชาชนเห็น
7.2 การจัดกลุ่มพื้นที่
ผูกเคสกับรหัสตำบล แล้วรวมเป็นอำเภอและจังหวัด (สิงห์บุรี 6 อำเภอ 43 ตำบล จาก kongvut/thai-province-data) ใช้ตำบลเป็นหน่วยพื้นฐาน เพราะเขต อปท. ไม่ตรงกับตำบลเสมอ
พื้นที่ไม่ชัด → กลุ่ม "รอระบุพื้นที่" ไม่เดาตำบล ย้ายกลุ่มเมื่อผู้ใช้แก้ตำแหน่ง
อยู่พื้นที่เดียวกันไม่ได้แปลว่าเป็นเหตุเดียวกัน เคสยังเก็บแยกกัน
AreaSummary มี เวลาที่สรุป, ขอบเขตพื้นที่, รายการเคสและเวอร์ชันที่ใช้คำนวณ, จำนวนเคสตามระดับ, ความต้องการที่พบ และจำนวนคนตามที่แจ้ง (ระบุว่าอาจซ้ำหรือยังไม่ยืนยัน ไม่รวมกับจำนวนเคส)
AreaSummary ส่งเฉพาะ area_code ไม่ส่งชื่อพื้นที่ Agent 2 แปลงรหัสเป็นชื่อจาก areas_singburi.csv ชุดเดียวกัน (หรือเพิ่มชื่อใน schema ภายหลังถ้าทีมต้องการ)
v1.3 (1 พ.ย. 2569): เพิ่ม urgent_incident_ids = เคสที่มี urgent_flags หรือ priority red ในพื้นที่นั้น จำนวนเคส = จำนวน incident_id ใน case_versions ซึ่ง Agent 2 ใช้เรียกดูรายละเอียดรายเคส พื้นที่ที่ไม่มีเคสเปิดแล้วส่งสรุปที่ case_versions ว่างเพื่อให้ลบออก case_version ของ event สรุปคือเวอร์ชันของสรุป ไม่ใช่ของเคส
ความสามารถเสริม (ไม่ใช่ MVP): Agent 2 วิเคราะห์ประกอบการพิจารณาระดับการจัดการสาธารณภัย 1–4 ระดับ 1 สั่งการที่อำเภอ/ท้องถิ่น ระดับ 2 ที่จังหวัด การประกาศระดับเป็นอำนาจของผู้บัญชาการ
7.3 การส่งต่อ Agent 2
ส่งทั้งรายเคส (event เดิมในข้อ 5) และสรุปพื้นที่ (event ใหม่) เคสด่วนส่งทันที ไม่รอรวมพื้นที่หรือข้อมูลครบ
ทุกการส่งมี event_id, case_version, occurred_at ฝั่งรับรับซ้ำได้อย่างปลอดภัย retry ไม่สร้างเคสหรือเพิ่มยอดซ้ำ และข้อมูลเก่าไม่ทับข้อมูลใหม่
ระบุ location_missing เมื่อยังไม่มีจุดเกิดเหตุ
รูปแบบข้อมูลและ transport รอทีม Agent 1–2 ตกลง (ข้อ 8.1)
v1.3 (1 พ.ย. 2569): ไฟล์ตัวอย่างที่ใช้อ้างอิงร่วมกับทีม Agent 2 มี 3 ไฟล์ สร้างจากโค้ดจริงและผ่าน validation ถ้า event เปลี่ยนต้องแก้ไฟล์ตัวอย่างพร้อมกัน
agent2_input_example.json — incident_submitted เคสใหม่
agent2_update_example.json — incident_updated เคสเปลี่ยน มี changes[] และ report ฉบับล่าสุด
agent2_area_summary_example.json — area_summary_updated สรุประดับตำบล/อำเภอ/จังหวัด
ตัวอย่างสรุปพื้นที่แสดงสภาพหลังตรวจรับรายชื่อพื้นที่แล้ว ก่อนตรวจรับทุกเคสอยู่ในกลุ่ม unassigned
7.4 สถานะดำเนินงาน
แยกสถานะการส่ง (delivery_status: pending / sent / acked / failed) ออกจากสถานะดำเนินงาน ส่งสำเร็จไม่เท่ากับเจ้าหน้าที่รับเรื่องแล้ว
มีช่องทางให้ Agent 2 หรือเจ้าหน้าที่บันทึกสถานะกลับ พร้อมตรวจสิทธิ์
แยกแหล่งที่มาของสถานะ: ผู้แจ้งบอกว่าช่วยแล้ว ≠ หน่วยงานยืนยันเสร็จสิ้น และกำหนดผู้มีสิทธิ์ปิดเคส
บอกประชาชนได้เฉพาะสถานะที่บันทึกกลับมาจริง เช่น "เจ้าหน้าที่รับเรื่องแล้ว" เมื่อมีคนบันทึกสถานะนั้นแล้วเท่านั้น
v1.3 (ร่างในโค้ด รอทีมตกลง): ค่าสถานะ received, in_progress, completed, reporter_resolved แหล่งที่มา agent2, official, reporter ผู้แจ้งบันทึกได้เฉพาะ reporter_resolved ทุกรายการมี recorded_by, reason, recorded_at ช่องทางรับคือ POST /incidents/operation ใช้ admin token และบันทึก audit
ข้อจำกัด: endpoint นี้ยังต้องใช้ user_id ภายในของ Agent 1 ซึ่ง Agent 2 ไม่มี (Agent 2 เห็นแค่ incident_id และ reporter_ref) ต้องแก้ให้ค้นจาก incident_id ก่อนทำไฟล์ตัวอย่างขาเข้าให้ทีม Agent 2
