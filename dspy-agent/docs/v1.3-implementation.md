# Agent 1 implementation against Design Decisions v1.3

The source requirements are preserved in [design-decisions-v1.3.txt](design-decisions-v1.3.txt).
Schema version is now `1.3`. The case priority rules and Agent 1–2 additions below
are implemented as a **draft contract**, pending team/expert agreement in section 8.1.
They have not become an approved operational triage policy merely by being implemented.

## Runtime

`FloodAgent` calls extraction, Python rules, `priority.py`, and `handoff.py`.
`runtime.py` integrates persistence, explicit contact consent, context, retention,
and response wording. `repository.py` stores versioned user snapshots and a
transactional outbox in PostgreSQL (`DATABASE_URL`) or SQLite for local development.
State is the source of truth; summaries never merge back into incident fields.

A submission and its new state commit together before transport or wording.
Urgent handoff is dispatched before wording; urgent responses use fixed short text
and one follow-up field. Each retry uses the original `event_id` and case version.
A received ACK must match the event ID and explicitly say `received: true`.
No configured handoff URL means `pending`, not an invented successful delivery.
The server retries pending/failed events every 30 seconds, up to five attempts.

`/chat` is a development/simulation interface: returning a response counts as successful
reply delivery. `/line/webhook` checks the signature, uses HMAC-SHA256 identifiers,
caches processed event responses, and records questions, hotline notices and consent
requests only after the Reply API succeeds. A failed reply can replay its cached
response without re-running intake. There is no LINE push. Unfollow changes activity
state and does not delete records or stop retention timers.

Run one API worker: user agents and their locks are cached per process. Multi-worker
coordination and recovery from a process crash between intake commit and webhook
receipt caching need an additional durable ingress transaction/lease design. This
is a deployment limit, not a claim of exactly-once processing across crashes.

## Privacy and location

Phones, national ID numbers and explicitly labelled house numbers are masked before
messages or diagnostics are retained and before Gemini. Unlabelled house numbers
and Thai personal names cannot be reliably identified by these regex rules.
Raw phone values exist only in a pending consent request or a separately consented
`ContactRecord`; they never enter incident reports or model context. Typing a phone
number does not grant permission. Declining the separate request erases its phone.
Pending-phone expiry has no assumed policy default; `CONTACT_PENDING_TTL_HOURS`
is opt-in until the team approves the duration and basis.

Every reported incident offers optional GPS alongside the area question; knowledge-only
messages do not. Location-only input is held temporarily for up to 24 hours without
creating a case. Once an incident is described, unsolicited coordinates require a
separate confirmation. GPS never automatically determines a confirmed tambon.
No LINE-provided street address is retained. Declining forwarding overrides the
legacy rescue/evacuation forwarding basis. Requesting erasure immediately revokes
consent and suspends coordinate forwarding; it also scrubs copies in state histories,
messages, cached responses and historical outbox payloads, and emits a deletion event.
Deletion completion/ACK is tracked in `deletion_requests`.

Retention maintenance implements draft abandonment after 7 days, submitted timeout
after 14 days, abandoned draft deletion after a further 30 days, message retention
of 90 days, and contact/coordinate erasure 30 days after closure. A timeout does not
mean safety. Erased historical events are not guaranteed replayable as original
valid payloads; emptied updates are cancelled and never delivered.

The first privacy notice is versioned and displayed once per notice version. It is
the short draft notice from the design, not a replacement for the full notice and
PDPA review required before real user trials.

## Response wording and knowledge

`response.py` calls DSPy only for non-urgent turns that need questions or supported
knowledge text. It receives the selected fields, confirmed state, recent redacted
messages and retrieved evidence. Facts in summaries, delivery status and hotline
blocks remain generated by Python. Validation failure or an exception immediately
uses templates; the composition adapter disables its extra JSON-format retry.

The model can now write new acknowledgement/question wording and paraphrase knowledge
from one or several retrieved rows. `question_hints` are guidance, not a whitelist
of literal strings. The response plan includes recent messages, confirmed state and
this turn's changes, with coordinates/contact values excluded. Python validates
that the requested fields are complete, already answered fields are not asked again,
extra field requests are rejected, numbers and explicit area names are grounded,
and citations refer only to retrieved rows. It also checks forbidden claims, personal
identifiers, phone numbers, polite endings and length. Citations are appended by code.

These structural/regex checks do not prove semantic equivalence or rule out every
possible unsupported Thai statement. This is the limitation acknowledged in section
6.8; factual summaries, delivery status and hotline blocks remain locked in code.
The wording limit is 1,200 characters, a configurable constructor default pending
measurements and team agreement. No measured Gemini latency or cost is claimed by
the offline tests.

`knowledge.py` loads CSV at startup and searches title, example questions and reviewed
text. Only approved rows with source/reviewer metadata are eligible; expired rows and
category B without a valid expiry are excluded. `knowledge_th.csv` now includes five sourced Core Safety candidates and nine
general knowledge candidates, all pending human review, with unfilled reviewer and
approval timestamps. Their source checks are recorded separately. See
[core-safety-review.md](core-safety-review.md) and [knowledge-review.md](knowledge-review.md)
for the sources and review checklist.
`core_snippets()` bypasses the retrieval score for relevant approved category-A rows;
`evidence_for()` merges these with ordinary retrieval and removes duplicates. The
approval/expiry guards still apply, and snippets are not broadcast automatically for
every urgent flag. No human approval was fabricated, so the shipped app continues
using the honest knowledge-unavailable fallback until the team approves the content. Embeddings/pgvector remain future work as required by v1.3.

Context uses the existing five-layer builder with a character budget. Rolling summaries
contain incident IDs only, intentionally sacrificing narrative detail to prevent names
and coordinates from being copied into summaries. Thresholds remain configurable.

## Areas, priorities and status

`areas_singburi.csv` includes the draft 6 districts / 43 tambons from
[kongvut/thai-province-data](https://github.com/kongvut/thai-province-data), retrieved
2026-11-01. It is attributed under the included MIT license. Every row is
`pending_review`, with `verified_at` empty. The resolver will not treat these rows
as verified until the team cross-checks them with official sources and marks them
approved. It matches exactly, uses supplied parent district names, and asks about
ambiguous/missing results without silently correcting spellings. GPS polygon
suggestions remain outside MVP.

`province_code` is the real province code `17`, not the source dataset's internal
sequence number. Names without ต./อ. prefixes match without spaces ("ทับยาอินทร์บุรี",
"น้ำตาลค่ะ"); a name nested inside a longer name is ignored ("สิงห์" in "สิงห์บุรี").
A tambon plus a different district narrows to the row matching both. A conflicting
pair, or a name that is both a district and a tambon ("อินทร์บุรี"), returns
`ambiguous` and the user is asked. Until rows are approved every name is `unverified`.

Case priority takes the highest matching draft rule, records reasons/time/history,
never automatically lowers a level after ordinary updates, and preserves manual
overrides. New hazard tags are `electrical_hazard` and `structural_risk`.
Priority is never shown to the public. Area rollups include source case versions,
`urgent_incident_ids` (cases with urgent flags or red priority), priority counts,
reported needs, reported people, and warnings about overlap and unverified counts.
Moving or closing cases publishes replacement/empty snapshots, not duplicate
increments. Urgent intake does not wait for the rollup; rollups are rebuilt by the
30-second background task. Before area rows are approved, all cases roll up under
`unassigned`.

Urgent keywords still flag hypothetical or knowledge questions ("ถ้าโดนงูกัดต้องทำยังไง").
This over-report is deliberate pending live Gemini tests (design 6.3, 8.1).

Operations and priority overrides require the configured admin bearer token.
Contact access also requires actor/reason and writes an audit record. The draft
operation vocabulary is `received`, `in_progress`, `completed`, `reporter_resolved`;
a reporter cannot record an official completion. `check_status` continues to answer
technical delivery only. This vocabulary, role policy and transport require team
agreement; no external Agent 2 connection is enabled by default.

Field statuses belong to `ReportedValue`, not every metadata field.

## Configure and verify

Copy `.env.example` to `.env` and supply your own secrets. Never commit `.env`.
`docker compose up --build` configures PostgreSQL. For local development, install
`requirements.txt`, `pytest`, and run:

```sh
cd dspy-agent
python -m pytest -q tests
uvicorn app.main:app --port 8010
```

Tests use fake/DummyLM outputs, SQLite and mocked HTTP. They do not constitute live
Gemini, LINE OA, PostgreSQL or Agent 2 end-to-end verification. Required external
reviews/data and the measurements in section 8.1 remain open.

## Notebooks

`lab/1/flood_chat.ipynb` imports the current application modules. It loads the same
hotline, area and knowledge files as the API and uses an isolated in-memory SQLite
repository with no Agent 2 sender. It demonstrates optional location, separate
consent and both event examples. (`flood_agent.ipynb`, a step-by-step exploration
notebook overlapping it and the tests, was removed.)

`lab/1/line_chat_live.ipynb` is an interactive chat against live Gemini with draft
knowledge labelled as unreviewed.

`lab/1/e2e_live_test.ipynb` runs the real API (`app.main` via `TestClient`, so the
lifespan, background worker, outbox and retry run) against live Gemini, a SQLite file
in a temporary folder, and an in-notebook Agent 2 stand-in that receives events over
HTTP and returns ACKs. It checks intake, memory across an API restart, case updates,
an immediate urgent handoff, the area summary and that every outbox event is acked.
LINE OA, PostgreSQL and the real Agent 2 are not exercised. The generic `guy01.ipynb`
course-chat example is separate from the flood intake implementation.
